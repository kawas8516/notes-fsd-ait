1. Introduction to the Document Object Model

The Document Object Model (DOM) is the browser's live, in‑memory, tree‑shaped representation of an HTML page. It is not the HTML file itself — it's the structured object tree the browser builds after parsing that file, and it's what JavaScript actually reads and mutates to change what's on screen.[1]

Fig. 1 — Every tag in the HTML source becomes a node in this tree; document is the entry point JavaScript uses to reach any of them.

window vs. document

window is the top-level global object in a browser — it represents the browser tab/window itself and holds things like setTimeout, location, and alert. document is a property of window and is specifically the entry point into the page's DOM tree.

Key point: the DOM is a live representation — mutate it (e.g. element.textContent = 'new') and the browser re-renders the visible page immediately; there's no separate "save" step.

2. Selecting and Manipulating DOM Elements

MethodReturnsNotes
document.getElementById('id')A single element or nullFastest; matches exactly one unique ID
document.getElementsByClassName('cls')Live HTMLCollectionUpdates automatically as the DOM changes
document.getElementsByTagName('div')Live HTMLCollectionAll elements with that tag name

const title = document.getElementById('main-title');
const firstCard = document.querySelector('.card');
const allCards = document.querySelectorAll('.card');   // static NodeList
allCards.forEach(card => console.log(card));

Reading and writing content

PropertyWhat it does
.textContentGets/sets plain text only (fast, ignores hidden elements, safe from HTML injection)
.innerTextGets/sets the rendered text (respects CSS visibility, triggers reflow — slower)
.innerHTMLGets/sets content as HTML markup, parsed and rendered
title.textContent = 'Updated Title';       // safest for plain text
title.innerHTML = '<em>Updated</em> Title';   // parses the <em> tag
Common pitfall (security): never assign untrusted/user-supplied data to innerHTML — it will be parsed and executed as real HTML/script, opening the page to Cross‑Site Scripting (XSS). Use textContent for any user-generated text.

const list = document.querySelector('#todo-list');

const li = document.createElement('li');
li.textContent = 'Buy milk';
list.appendChild(li);              // add

list.firstElementChild.remove();   // remove

list.children[0].textContent = 'Updated item'; // update

classList — the preferred way to toggle styling

Fig. 3 — classList lets JS toggle pre-defined CSS classes instead of writing individual style properties by hand.
const box = document.querySelector('.box');
box.classList.add('highlight');
box.classList.remove('hidden');
box.classList.toggle('open');          // flips it on/off
console.log(box.classList.contains('open'));
Best practice: prefer classList + CSS classes over directly setting element.style.xxx — it keeps presentation rules in the CSS file where they belong, and one class can toggle many properties at once.

5. Events and Event Listeners

An event is a signal that something happened (a click, a key press, a page finishing loading). addEventListener(type, handler) registers a function to run whenever that event occurs on an element.[2]

CategoryCommon event types
Mouseclick, dblclick, mouseover, mouseout, mousedown, mouseup, mousemove
Keyboardkeydown, keyup
Formsubmit, change, input, focus, blur
Document/windowDOMContentLoaded, load, resize, scroll
const btn = document.querySelector('#save-btn');

function handleClick(event) {
  console.log('Clicked element:', event.target);
  event.preventDefault();      // stop the default browser action (e.g. form submit/navigation)
}

btn.addEventListener('click', handleClick);
btn.removeEventListener('click', handleClick);  // needs the SAME named function reference

The event object

Property/methodMeaning
event.targetThe exact element the event originated on
event.currentTargetThe element the listener is actually attached to
event.typeThe event name, e.g. "click"
event.preventDefault()Cancels the browser's default behaviour for that event
event.stopPropagation()Stops the event from continuing to bubble/capture further

6. Event Delegation, Bubbling, and Capturing

When an event fires on a nested element, it travels through the DOM tree in three phases: it first captures downward from window to the target, reaches the target itself, then bubbles back upward to window.[3]

Fig. 4 — Both phases visit every ancestor; by default listeners run on the way back up (bubbling) unless the third argument requests capturing.

Event delegation — one listener for many children

Because events bubble, a single listener on a common parent can handle events from any of its current or future children by inspecting event.target. This avoids attaching (and re-attaching) a listener to every individual item.

// Instead of adding a click listener to every <li>...
document.querySelector('#todo-list').addEventListener('click', (event) => {
  if (event.target.matches('.delete-btn')) {
    event.target.closest('li').remove();
  }
});
// Works even for <li> items added to the list LATER —
// no need to re-bind a new listener to each new item.
Advantages of delegation
Fewer total event listeners → lower memory use, faster setup
Automatically covers elements added to the DOM after the listener was set up
One place to update the handling logic instead of many
Common pitfall: forgetting that stopPropagation() inside a child's own handler will prevent a delegated listener on an ancestor from ever seeing that event.

7. Virtual DOM vs. Real DOM — Conceptual Introduction

The Real DOM is the browser's actual, live tree — every direct mutation can trigger expensive layout recalculation (reflow) and repaint. Libraries like React introduced the Virtual DOM: a lightweight, in‑memory JavaScript object tree that mirrors the UI. When state changes, a new virtual tree is built and diffed against the previous one, and only the minimal set of real DOM changes needed is applied.[4]

AspectReal DOMVirtual DOM
What it isThe browser's live rendered treeA plain JS object tree mirroring the UI
Update costExpensive — reflow/repaint on every direct changeCheap — comparing JS objects has no rendering cost
Who updates itYour code, directly, when using plain JS DOM methodsThe library's reconciler, after diffing, in batched, minimal steps
Key point: this is a conceptual bridge to frameworks like React — plain JS (as in this unit) manipulates the real DOM directly, which is fine for small amounts of change, but becomes a performance bottleneck for apps with frequent, widespread UI updates, which is the problem the virtual DOM pattern was designed to solve.

8. Modern Best Practices — Separation of JS and HTML

"Unobtrusive JavaScript" is the practice of keeping structure (HTML), presentation (CSS), and behaviour (JS) in separate files/layers, connected only through IDs, classes, and data-* attributes — never mixed inline.

Fig. 5 — Each layer can be changed independently: redesign the CSS without touching JS, or change behaviour without editing markup.
<!-- Avoid: JS mixed directly into HTML -->
<button onclick="deleteItem()">Delete</button>
<div style="display:none;" id="panel">...</div>
// Prefer: HTML stays clean; behaviour lives in JS, styling in CSS
document.querySelector('#delete-btn').addEventListener('click', deleteItem);
document.querySelector('#panel').classList.toggle('is-hidden'); // CSS: .is-hidden { display: none; }
PracticeWhy
No inline onclick="" attributesKeeps behaviour in one place, easier to find/maintain, no HTML re-parsing per handler string
Toggle CSS classes, not inline stylePresentation rules stay centralised and cacheable in the stylesheet
Wrap script in DOMContentLoaded or place <script defer>Guarantees the DOM exists before your JS tries to select elements
Use data-* attributes to pass data to JSAvoids scattering "magic strings" through both HTML and JS
