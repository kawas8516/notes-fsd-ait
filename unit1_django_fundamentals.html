1. Django Architecture and the MVC / MVT Design Pattern

Django is a high‑level Python web framework built around the Model–View–Template (MVT) architecture — Django's own take on the classic Model–View–Controller (MVC) pattern.[1] In MVC, the Controller is code you write to receive a request, talk to the Model, and choose a View. In Django, that dispatching job is handled internally by the framework itself (the URL dispatcher + the Django core), so what a Django developer calls a "View" actually plays the role of the MVC Controller, while a Django "Template" plays the role of the MVC View.

MVC termDjango (MVT) equivalentResponsibility
ModelModel (models.py)Defines data structure; talks to the database via the ORM
ControllerView (views.py) + URL dispatcherReceives the request, runs business logic, decides what to send back
ViewTemplate (.html files)Presentation layer — how data is displayed

Request–response cycle

Fig. 1 — Browser sends a request → urls.py matches it to a view function/class → the view queries models.py and renders template.html with context → HTML flows back to the browser.
Key point: in Django, "the framework is the Controller." You never write a Controller class yourself — Django's URL resolver + your View function together perform that job.

Underlying theory: WSGI/ASGI and the request–response contract

A Django project is, underneath everything, a WSGI application (or ASGI application for async support) — a Python callable that a web server (Gunicorn, uWSGI, Daphne, Uvicorn…) invokes for every incoming HTTP request. wsgi.py and asgi.py expose this callable so external servers know how to talk to Django. Every view, no matter how it's written, must obey one contract: it receives an HttpRequest object and must return an HttpResponse object (or a subclass such as JsonResponse, HttpResponseRedirect, or raise an exception like Http404). Django's core simply threads this request object through middleware → URL resolver → view → middleware again, and ships the resulting response back to the server.

Design philosophy behind Django

Django's own documentation states a handful of guiding principles that explain why the framework looks the way it does:

  • Loose coupling: the layers of the stack (models, views, templates, URL config) don't need to know about each other's internals — you can change your templates without touching your models.
  • Less code: Django tries to let you express behaviour concisely — e.g. one line of URL config, one model class, instead of hand‑written SQL and boilerplate HTTP parsing.
  • Don't Repeat Yourself (DRY): the model is the single, definitive source of truth for your data — the admin site, forms, and validation all derive from it instead of re‑declaring fields elsewhere.
  • Explicit is better than implicit: URLs, imports, and configuration are written out rather than auto‑discovered by "magic" naming conventions (contrast with some other frameworks).

Key features of Django (frequent exam question)

  1. Rapid development: a complete admin interface, ORM, and forms system are generated largely from the model, so common CRUD apps can be built very quickly.
  2. "Batteries included": authentication, sessions, an admin site, form handling, and internationalization all ship with the core framework — no third‑party packages needed to get started.
  3. Built‑in security: Django protects against SQL injection (parameterised ORM queries), Cross‑Site Scripting (automatic template escaping), Cross‑Site Request Forgery (CSRF middleware/token), and clickjacking (X-Frame-Options middleware) by default.
  4. Object‑Relational Mapper (ORM): lets developers work with the database using Python classes and methods instead of raw SQL, while remaining portable across database engines.
  5. Scalability: a "shared‑nothing" architecture lets any layer (database, cache, application servers) be scaled independently by adding hardware.
  6. Versatility: used for content‑management systems, scientific computing platforms, social networks, and REST APIs (via Django REST Framework) alike.
  7. Automatic admin interface: django.contrib.admin introspects registered models and generates a ready‑to‑use CRUD interface for site administrators.
  8. Template engine: the Django Template Language separates presentation from business logic while supporting inheritance, filters, and tags.
  9. URL routing: a clean, centralised URLconf maps URL patterns to views rather than mapping URLs to files on disk.
  10. Open source and well‑documented: Django is released under the BSD licence and maintained by the Django Software Foundation with extensive official documentation.

2. Virtual Environments and Project Setup

A virtual environment is an isolated Python installation with its own site-packages, so that the Django version (and every other dependency) required by one project never conflicts with another project on the same machine.

Fig. 2 — Each project gets its own sandboxed environment, so dependency versions never collide.

Setup commands

terminal 
# 1. Create a virtual environment
python -m venv env

# 2. Activate it
# Windows (PowerShell):
env\Scripts\activate
# macOS / Linux:
source env/bin/activate

# 3. Install Django inside the venv
pip install django

# 4. Verify installation
django-admin --version

# 5. Create a new project
django-admin startproject myproject
cd myproject

# 6. Run the development server
python manage.py runserver

Freezing dependencies

# Save installed packages for teammates / deployment
pip freeze > requirements.txt

# Recreate the same environment elsewhere
pip install -r requirements.txt
Common pitfall: running pip install django without activating the venv first installs it globally, defeating the purpose of isolation. Always confirm the venv is active — the terminal prompt shows the env name in parentheses, e.g. (env) C:\projects\myproject>.

How isolation actually works

Every Python interpreter resolves import statements by searching directories listed in sys.path. When you run python -m venv env, Python creates a small, self‑contained directory tree (its own Scripts//bin/, Lib/site-packages, and a pyvenv.cfg marker file). Activating the environment simply prepends that venv's Scripts//bin/ folder to your shell's PATH, so typing python or pip resolves to the venv's copies rather than the system‑wide ones — and packages installed there land in the venv's private site-packages, invisible to any other project. This is why two projects on the same computer can depend on different, even incompatible, versions of Django without conflict.

pip itself is just a client for the Python Package Index (PyPI) — a public repository of published packages. requirements.txt is a plain‑text, pinned snapshot of exactly what pip resolved and installed, which is what makes a teammate's or a server's environment reproducible.

3. App Structure and Settings

A Django project is the whole website/configuration; a Django app is a self‑contained module inside it that does one job (e.g. "blog", "accounts"). One project can, and usually does, contain several apps.[2]

terminal 
django-admin startproject myproject
cd myproject
python manage.py startapp blog
Fig. 3 — myproject/ (outer) holds manage.py and the config package; each app (e.g. blog/) is a sibling folder with its own models, views, and migrations.
Note: seeing myproject/ appear twice is not a typo — django-admin startproject myproject deliberately creates an outer folder and, inside it, a same‑named inner package holding settings.py/urls.py. The outer folder is just a container (you can rename it freely); the inner one is the actual Python configuration package Django imports, so it's best left matching ROOT_URLCONF/WSGI_APPLICATION unless you deliberately update those settings too.

Registering the app

Every app must be added to INSTALLED_APPS before Django will recognise its models, templates, or template tags:

myproject/settings.py 
INSTALLED_APPS = [
    'django.contrib.admin',
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',
    'blog',                # ← our new app
]

Key settings.py variables

SettingPurpose
INSTALLED_APPSList of active apps (built‑in + yours)
DATABASESDB engine/credentials (SQLite by default)
TEMPLATESTemplate engine config — search paths, context processors
MIDDLEWAREOrdered list of request/response hooks (auth, sessions, CSRF, etc.)
ROOT_URLCONFDotted path to the project's main urls.py
ALLOWED_HOSTSHostnames allowed to serve the site (security check)
STATIC_URLURL prefix for CSS/JS/image assets
DEBUGShows detailed error pages when True — must be False in production

Why Django separates "project" from "app"

This split exists to encourage reusability: a well‑written app (say, a blog or a comments system) should ideally be droppable into any Django project with minimal changes, because it doesn't hard‑code anything about the site around it. Each app declares its identity and configuration through an AppConfig subclass in apps.py (auto‑generated by startapp), which Django uses to discover the app's models, signals, and default settings such as default_auto_field.

settings.py as plain Python

settings.py is not a special config format — it is an ordinary Python module, evaluated once when Django starts. This means settings can be computed (e.g. BASE_DIR = Path(__file__).resolve().parent.parent using pathlib) and can read from environment variables for values that must differ between environments:

import os
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent
SECRET_KEY = os.environ.get('DJANGO_SECRET_KEY')
DEBUG = os.environ.get('DJANGO_DEBUG', 'False') == 'True'

This "12‑factor" pattern — reading secrets and environment‑specific flags from the environment rather than hard‑coding them — is why DEBUG=True and a checked‑in SECRET_KEY are safe for local development but a serious security risk in production: a leaked SECRET_KEY lets an attacker forge session cookies, and DEBUG=True exposes stack traces, file paths, and settings values to any visitor who triggers an error.

Middleware — the request/response pipeline

Middleware is a chain of Python classes, listed in order in the MIDDLEWARE setting, that hook into every request/response. Each piece of middleware can inspect or modify the request on the way in (before it reaches the view) and the response on the way out (after the view returns) — like layers of an onion, with the view at the centre.

Fig. 3b — Each middleware can short‑circuit the chain (e.g. return a redirect early) or let the request continue inward; on the way back out, each layer gets a chance to modify the response too.
Common built-in middlewareJob
SecurityMiddlewareEnforces HTTPS, HSTS, and other security headers
SessionMiddlewareAttaches request.session, backed by the session store
CsrfViewMiddlewareValidates the CSRF token on unsafe requests
AuthenticationMiddlewareAttaches request.user based on the session
CommonMiddlewareHandles things like URL normalisation and Content-Length

A custom middleware is just a callable class with a fixed shape:

class SimpleTimingMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response   # next layer in the chain

    def __call__(self, request):
        # code here runs BEFORE the view
        response = self.get_response(request)
        # code here runs AFTER the view
        return response

4. URL Routing and Views

A URLconf maps URL patterns to views. Django tries each pattern in urlpatterns from top to bottom and calls the first view whose pattern matches the requested path.[3]

Fig. 4 — The URL dispatcher matches the path against each pattern and calls the matching view, passing any captured URL parameters as arguments.

Function‑based view (FBV)

blog/views.py 
from django.http import HttpResponse
from django.shortcuts import render, get_object_or_404
from .models import Post

def home(request):
    return HttpResponse("Welcome to the blog!")

def post_detail(request, id):
    post = get_object_or_404(Post, pk=id)
    return render(request, 'blog/post_detail.html', {'post': post})
blog/urls.py 
from django.urls import path
from . import views

app_name = 'blog'
urlpatterns = [
    path('', views.home, name='home'),
    path('blog/<int:id>/', views.post_detail, name='post_detail'),
]
myproject/urls.py (root) 
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('', include('blog.urls')),   # delegate to the app's URLconf
]

Class‑based view (CBV) equivalent

For simple display logic, Django's generic class‑based views remove boilerplate:

from django.views.generic import DetailView
from .models import Post

class PostDetailView(DetailView):
    model = Post
    template_name = 'blog/post_detail.html'
    context_object_name = 'post'   # available as {{ post }} in the template
Key point: include() lets each app own its own urls.py, keeping the project's root URLconf short and apps self‑contained/reusable.

Path converters

path() patterns use converters — <converter:name> — to both match and type‑cast the captured URL segment before it's handed to the view:

ConverterMatchesPython type passed to the view
str (default)Any non‑empty string, excluding /str
intOne or more digitsint
slugLetters, numbers, hyphens, underscoresstr
uuidA formatted UUIDuuid.UUID
pathAny string, including /str

For matching logic that converters can't express (e.g. multiple optional segments, custom regex), Django also provides re_path(), which uses raw regular expressions with named groups instead — the older, pre‑Django‑2.0 way of declaring URLs, still valid but more verbose.

How the resolver actually works

On every request, Django strips the domain and takes just the path portion of the URL, then walks ROOT_URLCONF's urlpatterns list in order, testing each entry. An include() entry only needs to match a prefix of the path — Django then hands the remaining portion of the path to that included URLconf to resolve further. This is why app URLs are typically written without a leading slash and why pattern order matters: a broad pattern placed before a specific one can "shadow" it and prevent it from ever being reached.

Function-based vs. class-based views

AspectFunction-based view (FBV)Class-based view (CBV)
Readability for simple logicVery explicit — easy to trace top to bottomMore boilerplate for a one‑off, custom view
Reuse of common patterns (list, detail, create, update, delete)You write the loop/query yourself every timeGeneric views (ListView, DetailView, CreateView…) implement these once, reused via inheritance
Extending behaviourCopy-paste or compose decoratorsOverride a specific method (e.g. get_queryset()) via mixins/subclassing
HTTP method dispatchManual if request.method == 'POST':Automatic — Django calls .get()/.post() methods on the class for you

5. Rendering Templates with Context Data

A view gathers data into a context dictionary and passes it to render(), which merges it into an HTML template written in the Django Template Language (DTL) — {{ variable }} for output, {% tag %} for logic like loops and conditionals.[4]

Fig. 5 — render() feeds the context dictionary into the template; the DTL engine substitutes every {{ }}/{% %} tag to produce plain HTML.

Passing and using context

blog/views.py 
def post_detail(request, id):
    post = get_object_or_404(Post, pk=id)
    comments = post.comments.all()
    context = {'post': post, 'comments': comments}
    return render(request, 'blog/post_detail.html', context)
templates/blog/post_detail.html 
{% extends "base.html" %}

{% block content %}
  <h1>{{ post.title }}</h1>
  <p>{{ post.body }}</p>

  <h3>Comments ({{ comments.count }})</h3>
  <ul>
    {% for c in comments %}
      <li>{{ c.author }}: {{ c.text }}</li>
    {% empty %}
      <li>No comments yet.</li>
    {% endfor %}
  </ul>
{% endblock %}

Template inheritance

A base layout defines shared structure once; child templates fill in the blocks:

templates/base.html 
<html>
<body>
  <nav>My Site</nav>
  {% block content %}{% endblock %}
</body>
</html>

Enabling template lookup

myproject/settings.py 
TEMPLATES = [
    {
        'BACKEND': 'django.template.backends.django.DjangoTemplates',
        'DIRS': [BASE_DIR / 'templates'],   # project-level templates folder
        'APP_DIRS': True,                   # also look inside each app's templates/
        'OPTIONS': {'context_processors': [
            'django.template.context_processors.request',
            'django.contrib.auth.context_processors.auth',
        ]},
    },
]
Common pitfall: forgetting {% extends %} must be the very first line of a child template, and every app's template folder should be namespaced (blog/templates/blog/post_detail.html) to avoid name clashes between apps.

Why templates deliberately have limited logic

The Django Template Language is intentionally not full Python — there's no arbitrary function calling or complex expressions inside {{ }}. This is a deliberate design choice to keep business logic in views/models (where it's testable) and presentation logic in templates, and to let designers work on templates without needing to understand — or accidentally break — the application's Python code. Anything more complex than simple attribute lookup, loops, and conditionals should be computed in the view and handed to the template as context.

Where variables like user and request come from

You never explicitly pass {'user': request.user} into every context dict, yet {{ user }} works in templates — this is the job of context processors, functions listed under TEMPLATES[0]['OPTIONS']['context_processors'] that automatically inject extra variables into every template's context. django.contrib.auth.context_processors.auth adds user and perms; django.template.context_processors.request adds request itself.

Template resolution order

When a template name like 'blog/post_detail.html' is requested, Django's template loaders search, in order: (1) each directory listed in TEMPLATES[0]['DIRS'], then (2) — if APP_DIRS is True — each installed app's own templates/ folder, in the order apps appear in INSTALLED_APPS. The first match wins, which is exactly why namespacing app templates under a subfolder named after the app avoids one app's base.html silently shadowing another's.

Automatic escaping (a security feature)

By default, every value rendered through {{ variable }} is HTML‑escaped — characters like <, >, and & are converted to their HTML entities. This is what stops a malicious <script> tag stored in, say, a comment field from executing in another user's browser (a Cross‑Site Scripting / XSS attack). Trusted, pre‑sanitised HTML can be rendered as‑is with the |safe filter or {% autoescape off %}, but only when you are certain the content isn't user‑supplied.
