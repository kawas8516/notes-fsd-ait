1.2 Features of Linux

Linux has become a widely popular operating system due to several core features and philosophical tenets that distinguish it from commercial alternatives like Windows. According to the sources, the following five features have been instrumental in its success:

  1. Open Source Accessibility and Cost: Most versions of Linux are freely available, and the underlying source code is open to the public. This allows a global community of developers to continuously enhance the software, fix security vulnerabilities, and add new features, ensuring the system grows at an impressive rate compared to proprietary software.
  2. Granular Control through the Command Line (CLI): Unlike other operating systems that often "shelter" users from the inner workings of the system, Linux emphasizes the Command Line Interface (CLI) as a source of power. The CLI allows for much greater precision and control, offering a wide variety of options in commands that are frequently hidden or unavailable in standard graphical interfaces.
  3. Dominance in Server and Network Infrastructure: Linux is the principal operating system for Internet infrastructure, including a majority of the world's web, mail, database, and domain name servers. Its stability and reliability make it the preferred choice for high-stakes environments like web hosting and supercomputing.
  4. Hardware and Platform Versatility: Linux is remarkably portable and can run on a vast range of devices. This includes everything from massive mainframes and supercomputers to handheld devices like Android-based smartphones, as well as specialized hardware such as routers, firewalls, and WiFi access points.
  5. Resource Efficiency: Linux distributions are often designed to be lightweight, requiring fewer system resources (CPU and memory) to run effectively than many other mainstream operating systems. Because many of its operations can be performed via text-based interfaces rather than resource-heavy graphical ones, it often runs faster on the same hardware.

1.3 Linux Philosophy

The philosophy of Unix and Linux centers on modularity, simplicity, and the concept that "everything is a file." This approach emphasizes building small, cohesive tools that perform one task well and can be easily combined to solve complex problems.

Everything is a File

One of the most fundamental tenets is that almost every entity in the operating system—including physical hardware, directories, and communication channels—is treated as a file. This abstraction allows users to apply the same set of standard commands (like cp, mv, or rm) and redirection operators to a wide variety of system components.

  • Example: In Linux, physical storage devices like hard drives are represented as files in the /dev directory (e.g., /dev/sda1). Because they are treated as files, a system administrator can use standard redirection to communicate with them or obtain information about them using tools like stat just as they would with a regular text document.

Modularity and Chaining (Pipes)

The Unix philosophy encourages high cohesion (tools that do one thing specifically) and low coupling (tools that don't depend heavily on each other). Instead of creating massive, monolithic programs, Linux provides specialized tools that communicate via text streams. These tools can be chained together using a pipe (|), which sends the output of one program to serve as the input for another.

  • Example: If a user wants to count how many files in a directory are readable and writable, they don't need a specific "permission counter" application. Instead, they can chain three small tools together: ls -l (to list files with permissions), grep "^-rw" (to filter for lines starting with file permissions for read/write), and wc -l (to count those lines). This modularity allows for nearly infinite flexibility without requiring complex new software for every unique task.

User Control and Openness

The philosophy also prioritizes transparency and control over a "sheltered" user experience. The command line is viewed as the source of power, offering precision that graphical interfaces often hide. This is reinforced by the Open Source movement, which dictates that software should be free to study, change, and improve. This openness ensures that the community can continuously refine the kernel and applications, fostering a culture of experimentation and learning.

1.5 Shell

1.5.1 What is a Shell

A shell is a program that allows you to interact with the Linux operating system using commands.

Examples:

  • Bash
  • Zsh
  • Fish

A shell is a user interface that acts as a layer between the user and the core components of the operating system, known as the kernel. It provides a user-tailored environment that includes a command-line interface (CLI), an interpreter, and an environment of previously defined entities like variables, functions, and command shortcuts called aliases. The interpreter's primary role is to accept user input, translate the commands into executable code, and execute them. Users typically interact with a shell through a terminal window in a graphical interface or by logging into a text-based environment.

Different Shells Available in Linux

While many shells have been developed over the years, they generally fall into two main families: those based on the Bourne shell and those based on the C shell.

  • Thompson Shell: This was the earliest shell, introduced in Unix in 1971.
  • Bourne Shell (sh): Released in 1977 and named after its author, Stephen Bourne, it introduced fundamental features like shell scripts, redirection, pipes, and typeless variables.
  • C Shell (csh): Written by Bill Joy in the late 1970s, this shell uses a syntax largely based on the C programming language. It introduced several modern features now found in most shells, such as history, aliases, and command-line editing.
  • TC Shell (tcsh): A variation of the C shell developed between 1975 and 1983, it added greater operability for accessing commands in the history list.
  • KornShell (ksh): Developed by David Korn in 1983, it shares many features with the C shell but includes WYSIWYG-style command-line editing and support for floating-point variables.
  • Almquist Shell (ash): A smaller, faster variation of the Bourne shell released in 1989 for computers with modest resources. It has largely been replaced in many systems by a newer version called dash.
  • Bourne-Again Shell (Bash): Released in 1989 by Brian Fox for the GNU project, it is the default shell for most Linux distributions. It is an extension of the Bourne shell and incorporates the best features of the C and TC shells, including advanced command-line editing and tab completion.
  • Z Shell (zsh): Released in 1990 as an extension of both the Bourne and Korn shells, it adds unique features like automated spelling correction, customizable prompts, and modules for mathematical and network computations.
  • Specialized Language Shells: Some shells have been adapted to support specific programming languages, such as Rhino/BeanShell (Java), psh (Perl), sqsh (SQL), and scsh (Scheme).

1.5.2 Shell Environment

In the Linux shell, your environment is tailored through the use of variables, redirection, pipes, and filters. These tools allow you to manage data streams and automate complex tasks by combining simple commands.

1. Environment Variables

A variable is a name that references a value stored in memory. Environment variables are predefined variables used by the operating system and other programs to determine how the system behaves.

  • Viewing Variables: Use the env command to see all defined environment variables.
  • Accessing Values: Precede the variable name with a $ (e.g., echo $HOME).
  • Common Examples:
    • HOME: Stores the path to the user's home directory.
    • PWD: Stores the current working directory.
    • PATH: A list of directories the shell searches to find executable programs when a command is entered.
    • PS1: Defines the appearance of the command-line prompt.
2. Redirection

Redirection allows you to change where a command receives its input or sends its output. By default, standard input (STDIN) comes from the keyboard, and standard output (STDOUT) and standard error (STDERR) go to the terminal window.

  • Output Redirection (> and >>):
    • > sends output to a file, overwriting it (e.g., ls > file_list.txt).
    • >> appends output to the end of an existing file (e.g., date >> log.txt).
  • Input Redirection (< and <<):
    • < uses a file as input for a command (e.g., wc -l < data.txt).
    • << (Here Document) reads input from the keyboard until a specific delimiter string is typed (e.g., cat << done > newfile.txt reads until the user types "done").
3. Pipes

A pipe (|) is a specific form of redirection that sends the output of one command to serve as the input for the next command. This allows for "chaining" multiple commands together to perform complex data processing.

  • Example: To count the number of files in a directory, you can pipe the output of ls into the wc (word count) tool: ls -1 | wc -l.
4. Filters

Filters are programs that accept a stream of text as input, process it (e.g., searching, sorting, or modifying), and then output the result. They are almost always used in conjunction with pipes.

  • Common Filter Examples:
    • grep: Searches for lines that match a specific regular expression pattern. Example: ps aux | grep bash (filters the process list for only those containing "bash").
    • sort: Sorts the lines of text alphabetically or numerically. Example: cat names.txt | sort.
    • uniq: Removes consecutive duplicate lines from a sorted file.
    • sed: A stream editor used to search for and replace strings within a text stream. Example: echo "Hello World" | sed 's/World/Linux/' (outputs "Hello Linux").
    • awk: A powerful pattern-scanning and processing language used to extract and manipulate specific data fields. Example: ls -l | awk '/^-/ {print $5, $9}' (filters for regular files and prints only their size and name).

2.2 Process and Service Management

In Linux, the management of system activity is handled through two closely related concepts: processes and services (also known as daemons). While a service is technically a type of process, they differ in their intended purpose and how they are handled by the system.

Processes vs. Services

  • Process: A process is defined as any running program. It is an "active entity" that contains code, has memory space for data, and possesses a specific state (such as its current instruction and register values). Every process is assigned a unique Process ID (PID) for tracking.
  • Service (Daemon): A service is a specific type of process that runs in the background to handle requests from users, applications, or other system components on demand. Unlike standard application processes that a user might interact with directly, services usually lack a user interface and remain idle until they are called upon.
  • Key Difference: While most processes are started by users to perform a specific task and terminate once that task is done, services are typically started during system initialization and remain available throughout the entire session to provide ongoing support for system functions like networking, printing, or scheduling.

Managing Processes in Linux

Linux uses several commands to monitor and control the lifecycle of processes:

  • Monitoring:
    • ps (Process Status): Provides a snapshot of currently running processes. Common options like ps aux show processes for all users across the system.
    • top: An interactive, text-based tool that provides real-time updates on resource utilization (CPU, memory) and active processes.
    • jobs: Displays processes that are currently suspended or running in the background within the specific terminal window.
  • Control and Prioritization:
    • kill and killall: Used to terminate processes. kill requires a specific PID, while killall can terminate all instances of a process by its name.
    • bg and fg: Used to move processes between the background and foreground within a shell session.
    • nice and renice: These adjust a process's niceness value, which determines its priority; a higher niceness value means the process is "nicer" to others and receives less CPU time.

Managing Services in Linux

Services are managed through specific administrative tools and configuration files:

  • service: This command-line utility is used to start, stop, restart, or check the status of a specific service (e.g., /sbin/service atd status).
  • /etc/init.d/ Scripts: This directory contains the actual controlling scripts for services. System administrators can invoke these scripts directly to manage a service (e.g., ./nfs start).
  • chkconfig: Used to view or alter which runlevels a service is configured to start or stop in automatically during system initialization.
  • systemctl: In newer Linux distributions that use the systemd init system (such as Fedora or Ubuntu), systemctl is the primary command used to enable, disable, start, or stop services.
  • Configuration Files: Most services are tuned using text-based configuration files, typically located in the /etc directory. For example, the rsyslog service is configured via /etc/rsyslog.conf.

2.3 Soft and Hard Links

In Linux and Unix-based systems, links are mechanisms that allow a single file to be referenced by multiple names or from multiple locations within the file system. They are categorized into two types: hard links and soft (symbolic) links.

1. Hard Links

A hard link is essentially an additional name for an existing file's data.

  • Implementation: Technically, a directory in Linux is a list of entries where each entry maps a filename to an inode number. An inode is a data structure that stores all information about a file (permissions, owner, size, timestamps) except its name and the actual data blocks. A hard link is simply a new entry in a directory that points to an existing inode number.
  • Behavior: Because multiple hard links point to the same inode, they are all "original" copies of the file. If you modify the content through one link, it changes for all.
  • Persistence: Each file has a link count stored in its inode. When you delete a hard link, the system decrements this count. The actual data and the inode are only deleted from the disk when the link count reaches zero.

2. Soft (Symbolic) Links

A soft link, or symbolic link (symlink), is a special type of file that contains a text string representing the path to another file or directory.

  • Implementation: Unlike hard links, a soft link has its own unique inode number and its own data blocks, which store the destination path. It acts as a pointer to the original file's name.
  • Behavior: When the operating system accesses a symlink, it sees the "pointer" and automatically redirects the request to the target path. In a long listing (ls -l), symlinks are identified by the character l and an arrow showing the target (e.g., link -> /path/to/file).
  • Persistence: If the original file is moved or deleted, the symlink remains but becomes "broken" or "dangling," because the path it points to no longer exists. Deleting the symlink itself has no effect on the original file.

Why do we have both types?

The two types of links serve different functional needs based on their limitations and strengths:

Feature Hard Links Soft (Symbolic) Links
Cross-Partition No. Cannot link files across different disk partitions or file systems. Yes. Can point to files on different partitions or even remote network drives.
Directories Usually No. Hard linking directories is restricted to prevent circular loops. Yes. You can link to directories as easily as files.
Data Safety High. The file data exists as long as at least one hard link remains. Lower. If the target is deleted, the link becomes useless.
Use Case Useful for data redundancy within a partition or making the same data accessible under different names. Ideal for creating shortcuts, organizing system libraries, or maintaining references to files that might be updated/moved.

Example:

3.2 Package Management Overview

Package management is the process of installing, updating, removing, and managing software packages and their dependencies.

Role in DevOps

Package management helps DevOps teams:

  • Install software consistently

  • Manage dependencies

  • Automate server setup

  • Keep software updated

  • Roll back problematic versions

  • Maintain reproducible environments

Package management systems are essential tools in Linux that automate the process of installing, updating, configuring, and removing software. Instead of requiring a system administrator to manually compile source code or track file placements, these systems manage these tasks efficiently.

How Package Management Helps

  • Automatic Dependency Resolution: This is one of the most critical benefits. Many programs require specific software libraries (shared object files like .so files) to function. Package managers identify these needs and automatically install the required libraries, preventing "dependency hell".
  • Integrity and Security Checks: They use checksums and digital signatures to verify that packages are legitimate and have not been tampered with.
  • Simplified Maintenance: They facilitate clean software updates, patches, and removals. When removing software, they identify all associated files and only delete those that are not needed by other installed packages.
  • Efficiency: They save significant time and reduce the likelihood of human error compared to manual installation.

3.3 RPM (Red Hat Package Manager)

RPM is a core, lower-level package management tool used primarily in Red Hat-based distributions like CentOS and Fedora.

  • Package Format: RPM files are archives compressed with gzip. They use a standard naming convention: software_name-version-release.architecture.rpm.
  • Functionality: It can install, upgrade, or erase software, but it is primitive in that it does not automatically handle dependencies. If a package is missing a required library, RPM will simply report an error, leaving the user to find and install the missing piece manually.
  • Core Commands:
    • rpm -i: Installs a package.
    • rpm -U: Upgrades an existing package or installs it if not present.
    • rpm -e: Erases (removes) a package.
  • Building Packages: Advanced users use "spec files" to define how an RPM should be built, including its dependencies and build instructions.

3.4 YUM (Yellowdog Updater, Modified)

YUM is a package manager traditionally used in Red Hat-based Linux distributions such as RHEL and CentOS.

Modern RHEL-based systems use DNF, which is the successor to YUM. yum is often retained as a compatibility command.

YUM is a high-level package management tool that acts as a front-end for RPM. It was designed to overcome the limitations of RPM.

Purpose of YUM

YUM is used to install, update, remove, and manage software packages and their dependencies.

User
  ↓
YUM
  ↓
Repository
  ↓
Package + Dependencies
  ↓
Linux System
  • Automation: Unlike RPM, YUM automatically resolves dependencies by searching pre-configured online repositories and downloading all necessary files in one go.
  • Repositories: Users do not need to manually download package files first; YUM fetches them directly from the internet.
  • Scalability: It can be used to manage updates across a server farm and can be scheduled to run automatically to keep systems patched.

Use Case

Suppose you need Nginx on a server:

sudo yum install nginx -y

YUM will:

  1. Find Nginx in the configured repository.

  2. Find required dependencies.

  3. Download the packages.

  4. Install them.

yum update vs yum upgrade

Command Meaning
yum update Updates installed packages to newer available versions
yum upgrade Also updates packages, generally allowing replacement/removal of packages when required by dependency changes

For basic exam/interview understanding:

update → update existing packages
upgrade → update packages + handle dependency changes more aggressively

Core Commands

  • yum install [package]: Finds, downloads, and installs software.
  • yum update: Upgrades specified packages or the entire system if no package is named.
  • yum remove: Uninstalls software cleanly.
  • yum check-update: Lists available upgrades without installing them.
# Install
sudo yum install nginx -y

# Update all packages
sudo yum update

# Remove package
sudo yum remove nginx

# Search for a package
yum search nginx

# Show package information
yum info nginx

# List installed packages
yum list installed

# Check available updates
yum check-update

-y means automatically answer "yes" to confirmation prompts. The -y option allows YUM to run without user interaction by automatically assuming "yes" to all prompts.

Evolution

In recent distributions, YUM is being replaced by dnf, which is a compatible rewrite with the same command-line interface.
