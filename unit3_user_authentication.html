1. Built-in User Authentication

Django ships with a complete authentication system in django.contrib.auth — a User model, session‑based login tracking, permissions/groups, and ready‑made views for login, logout, and password management.[1] It's enabled by default whenever django.contrib.auth and django.contrib.sessions are in INSTALLED_APPS (they are, in every new project).

Fig. 1 — authenticate() verifies credentials; login() stores the authenticated user in the session so request.user is populated on every later request.

Protecting views

from django.contrib.auth.decorators import login_required

@login_required(login_url='login')
def dashboard(request):
    return render(request, 'dashboard.html')
templates/dashboard.html 
{% if user.is_authenticated %}
  <p>Welcome back, {{ user.username }}!</p>
{% else %}
  <p><a href="{% url 'login' %}">Log in</a></p>
{% endif %}

Wiring up the built-in URLs

Rather than writing login/logout views from scratch, most projects include Django's ready‑made auth URLconf:

myproject/urls.py 
from django.urls import path, include

urlpatterns = [
    path('accounts/', include('django.contrib.auth.urls')),
    # provides: login/, logout/, password_change/, password_reset/, etc.
]
Key point: Django never stores plain‑text passwords — authenticate() hashes the submitted password (PBKDF2 by default) and compares it to the stored hash.

Authentication backends (pluggable verification)

authenticate() doesn't hard‑code "check the User table" — it delegates to an ordered list of authentication backends defined in the AUTHENTICATION_BACKENDS setting (by default just ModelBackend, which checks Django's own User table). Django tries each backend in order and returns the first successful match; this is the mechanism that lets you plug in LDAP, OAuth/SSO, or "log in with email instead of username" without changing any view code — you simply add a custom backend class implementing authenticate() and get_user().

Permissions and groups

Beyond "is this user logged in," Django's auth system layers on an authorization model: every user has boolean flags is_active, is_staff (can access the admin site), and is_superuser (bypasses all permission checks). Finer‑grained access uses permissions — automatically created for every model as add_<model>, change_<model>, delete_<model>, view_<model> — which can be assigned directly to a user or, more manageably, bundled into a Group (e.g. "Editors") that many users join. Views check these with user.has_perm('blog.change_post') or the @permission_required decorator.

How passwords are actually hashed

Django never stores a raw or reversibly‑encrypted password — only a one‑way hash. The PASSWORD_HASHERS setting lists hashing algorithms in preference order (PBKDF2 by default; Argon2 is recommended if the argon2-cffi package is installed). Each stored hash also embeds which algorithm and how many iterations produced it, which is what lets Django transparently upgrade a user's stored hash to a stronger algorithm the next time they successfully log in, without ever needing to know their plaintext password in advance.

Authentication vs. Authorization (frequent exam question)

AspectAuthenticationAuthorization
Question it answers"Who are you?""What are you allowed to do?"
HappensFirst — at login, via authenticate()/login()After — on every protected action, via permission checks
Django mechanismAuth backends, sessions, request.userPermissions, Groups, is_staff/is_superuser, has_perm()
Example check"Is this really the user ada?""Can ada delete this blog post?"

The two are independent and sequential: a user must first be authenticated (identity confirmed) before Django even has a meaningful request.user to run authorization checks against. An anonymous (not‑logged‑in) user is represented by AnonymousUser, which always fails every permission check.

The Django admin site (built on the same auth system)

django.contrib.admin is a ready-made management UI generated from your registered models, and it reuses the exact same authentication system covered above — the same User table, the same hashed passwords, the same sessions. Only users with is_staff=True may log into /admin/, and what they can see/edit there is governed by the same permission objects (add_*, change_*, delete_*, view_*).

# Create an admin (superuser) account — bypasses all permission checks
python manage.py createsuperuser

2. Login

The simplest way to add a login page is Django's built-in class‑based LoginView, which handles displaying the form, validating credentials, and creating the session automatically.[2]

Fig. 2 — LoginView renders the form on GET, and on a valid POST calls authenticate() + login() before redirecting.

Using the built-in LoginView

myproject/urls.py 
from django.contrib.auth import views as auth_views
from django.urls import path

urlpatterns = [
    path('login/', auth_views.LoginView.as_view(template_name='registration/login.html'), name='login'),
]
templates/registration/login.html 
<h2>Log In</h2>
<form method="post">
  {% csrf_token %}
  {{ form.as_p }}
  <button type="submit">Log In</button>
</form>
myproject/settings.py 
LOGIN_REDIRECT_URL = 'dashboard'   # where to send users after a successful login

Writing your own login view (manual approach)

from django.contrib.auth import authenticate, login
from django.shortcuts import render, redirect

def login_view(request):
    if request.method == 'POST':
        username = request.POST['username']
        password = request.POST['password']
        user = authenticate(request, username=username, password=password)
        if user is not None:
            login(request, user)
            return redirect('dashboard')
        return render(request, 'registration/login.html', {'error': 'Invalid credentials'})
    return render(request, 'registration/login.html')
Common pitfall: forgetting {% csrf_token %} inside the <form> — Django rejects the POST with a 403 Forbidden error without it.

How "being logged in" is remembered: the session framework

HTTP itself is stateless — the server has no memory of a previous request. Django simulates persistent login using the session framework: when login() succeeds, Django creates a session record (by default stored server‑side in the database, in a table managed by django.contrib.sessions) keyed by a random session ID, and sends that ID to the browser as an HTTP‑only cookie (sessionid). On every subsequent request, SessionMiddleware reads that cookie, looks up the matching session record, and attaches the associated user to request.user — this is the entire mechanism behind "staying logged in" across page loads.

Why {% csrf_token %} is required

Cross‑Site Request Forgery (CSRF) is an attack where a malicious site tricks a logged‑in user's browser into submitting a request to your site (the browser automatically attaches the session cookie, so the request looks legitimate). Django's CsrfViewMiddleware defends against this by requiring every unsafe request (POST, PUT, DELETE…) to include a secret, per‑session token that only pages actually served by your own site would know — {% csrf_token %} renders that hidden token into the form. A request missing or presenting the wrong token is rejected with 403 Forbidden before it ever reaches your view.

3. Logout

Logging out simply clears the user's session data. Django's LogoutView does this in one line of URL configuration — no template is required unless you want a custom confirmation page.[2]

myproject/urls.py 
from django.contrib.auth import views as auth_views

urlpatterns = [
    path('logout/', auth_views.LogoutView.as_view(next_page='login'), name='logout'),
]
templates/base.html 
<form method="post" action="{% url 'logout' %}">
  {% csrf_token %}
  <button type="submit">Log Out</button>
</form>
myproject/settings.py 
LOGOUT_REDIRECT_URL = 'login'   # used if next_page isn't set on the view
Key point: since Django 4.1, LogoutView only accepts POST requests (a plain <a href="/logout/"> link no longer works) — this prevents logout being triggered by a malicious link (CSRF‑style attack). Always log out via a form/button.

What happens to the session on logout

logout() doesn't just "forget" the user — it calls request.session.flush(), which deletes the session record from the backend entirely and generates a brand‑new, empty session (with a new session ID) for the now‑anonymous request. This distinguishes an explicit logout from mere session expiry (governed by SESSION_COOKIE_AGE, default two weeks), where the session simply becomes invalid after a timeout without the user taking any action. Flushing rather than just marking the session inactive also protects against session fixation attacks, where an attacker who obtained an old session ID could otherwise reuse it.

4. User Registration

Django does not ship a ready‑made registration view, but it provides UserCreationForm — a form with username, password1, and password2 fields plus built‑in password‑matching and strength validation — that you plug into your own view.[3]

Fig. 3 — UserCreationForm validates the two password fields match and meet Django's password validators, hashes the password, then saves a new User row.

Function-based registration view

accounts/views.py 
from django.contrib.auth.forms import UserCreationForm
from django.shortcuts import render, redirect

def signup_view(request):
    if request.method == 'POST':
        form = UserCreationForm(request.POST)
        if form.is_valid():
            form.save()
            return redirect('login')
    else:
        form = UserCreationForm()
    return render(request, 'registration/signup.html', {'form': form})

Class-based equivalent

from django.contrib.auth.forms import UserCreationForm
from django.urls import reverse_lazy
from django.views.generic import CreateView

class SignUpView(CreateView):
    form_class = UserCreationForm
    template_name = 'registration/signup.html'
    success_url = reverse_lazy('login')
templates/registration/signup.html 
<h2>Create Account</h2>
<form method="post">
  {% csrf_token %}
  {{ form.as_p }}
  <button type="submit">Sign Up</button>
</form>
accounts/urls.py 
from django.urls import path
from .views import signup_view

urlpatterns = [
    path('signup/', signup_view, name='signup'),
]

Extending the built-in User (custom fields)

To add extra fields (e.g. phone number) without replacing the whole auth system, use a one‑to‑one profile model:

from django.db import models
from django.contrib.auth.models import User

class Profile(models.Model):
    user = models.OneToOneField(User, on_delete=models.CASCADE)
    phone = models.CharField(max_length=15, blank=True)
    avatar = models.ImageField(upload_to='avatars/', blank=True)
Common pitfall: using form.save() directly with a plain ModelForm on User stores the raw password. Always use UserCreationForm (or call user.set_password()) so the password is hashed before saving.

Password strength rules: AUTH_PASSWORD_VALIDATORS

UserCreationForm's "meets Django's password validators" check refers to the AUTH_PASSWORD_VALIDATORS setting — an ordered list of validator classes that full_clean() runs the candidate password through. The default project template enables four: minimum length, a check against the user's own attributes (so a password can't just be the username), a check against a list of the most common leaked passwords, and a check that it isn't entirely numeric. Each is independently pluggable/configurable, so a project can add stricter rules (e.g. requiring a symbol) by writing one more validator class.

AUTH_PASSWORD_VALIDATORS = [
    {'NAME': 'django.contrib.auth.password_validation.UserAttributeSimilarityValidator'},
    {'NAME': 'django.contrib.auth.password_validation.MinimumLengthValidator'},
    {'NAME': 'django.contrib.auth.password_validation.CommonPasswordValidator'},
    {'NAME': 'django.contrib.auth.password_validation.NumericPasswordValidator'},
]

Why a custom user model is usually recommended

Django's docs advise that if you're starting a new project, you should seriously consider swapping in a custom user model from day one — even if it looks identical to the default — by subclassing AbstractUser and pointing AUTH_USER_MODEL = 'accounts.User' at it. The reason is structural: AUTH_USER_MODEL can only be changed at the very start of a project, before the first migrate runs, because every other app's ForeignKey(User, ...) relationships are baked into migrations that reference it. The lightweight Profile (OneToOneField) approach shown above sidesteps this constraint and is fine for adding a few extra fields later in a project's life, but it can't rename or remove fields already on the built‑in User model.
