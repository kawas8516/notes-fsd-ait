1. Creating Models

A Django model is a Python class that describes one database table: each class attribute maps to a table column, and each model instance maps to one row. Models live in models.py and inherit from django.db.models.Model. Django's ORM (Object‑Relational Mapper) turns your Python code into SQL automatically, so you rarely write raw SQL.[1]

Basic model definition

blog/models.py 
from django.db import models
from django.contrib.auth.models import User

class Author(models.Model):
    name = models.CharField(max_length=100)
    bio = models.TextField(blank=True)

    def __str__(self):
        return self.name


class Post(models.Model):
    title = models.CharField(max_length=200)
    body = models.TextField()
    published_date = models.DateTimeField(auto_now_add=True)
    is_published = models.BooleanField(default=False)
    author = models.ForeignKey(Author, on_delete=models.CASCADE, related_name='posts')

    class Meta:
        ordering = ['-published_date']

    def __str__(self):
        return self.title


class Comment(models.Model):
    post = models.ForeignKey(Post, on_delete=models.CASCADE, related_name='comments')
    author = models.ForeignKey(User, on_delete=models.CASCADE)
    text = models.TextField()
    created_at = models.DateTimeField(auto_now_add=True)

What an ORM actually does

An Object‑Relational Mapper translates between two mismatched worlds — Python objects (with attributes, methods, inheritance) and relational database tables (rows, columns, foreign keys). Without one, every query would mean hand‑writing SQL strings and manually mapping result rows back into objects. Django's ORM generates that SQL for you based on the model class and the specific database backend configured in DATABASES (SQLite, PostgreSQL, MySQL, Oracle…), which is also what makes it possible to switch database engines with very little application code change.

QuerySets are lazy

A crucial theoretical point: writing Post.objects.filter(is_published=True) does not hit the database immediately. It builds a QuerySet object — a description of the query — which is only translated into actual SQL and executed when it is evaluated: by iterating over it, calling len(), slicing with a step, or calling list() on it. This laziness lets you chain filters efficiently:

qs = Post.objects.filter(is_published=True)   # no query yet
qs = qs.filter(author__name='Ada')             # still no query — just refines the description
posts = list(qs)                                # NOW Django builds and runs one combined SQL query

Each model also gets a default Manager, accessed as Post.objects, which is the entry point for all such queries; you can define custom managers to encapsulate commonly‑used filters (e.g. Post.published.all()).

Validation theory

Field arguments like max_length or blank=False are not automatically enforced when you call .save() — the ORM trusts you at the database layer (though the DB column type, e.g. VARCHAR(200), provides a hard backstop). Full validation (running each field's validators, checking blank/null rules, custom clean() logic) only happens when you explicitly call full_clean(), or implicitly when a ModelForm validates user input. This separation exists because not every object creation path (e.g. data migrations, scripts) should be forced through form‑style validation.

Advantages of using an ORM (frequent exam question)

  1. Database portability: the same model code can target SQLite, PostgreSQL, MySQL, or Oracle by changing only DATABASES, since the ORM generates the dialect-specific SQL.
  2. Less boilerplate: no manual connection handling, cursor management, or result-row‑to‑object mapping.
  3. Security by default: QuerySet parameters are automatically escaped/parameterised, which is what prevents SQL injection in ordinary usage.
  4. Pythonic, chainable syntax: filtering, ordering, and joining related tables reads like Python (Post.objects.filter(...).order_by(...)) instead of string-built SQL.
  5. Single source of truth: the model definition simultaneously drives the database schema, the admin site, and form validation (DRY).
  6. Automatic relationship handling: ForeignKey/ManyToManyField give you reverse lookups (author.posts.all()) and join queries without writing JOIN SQL by hand.

2. Creating and Applying Migrations

Migrations are Django's version‑control system for your database schema. Instead of hand‑writing SQL, you change your Python models and let Django generate — and later apply — the equivalent schema changes.[2]

Fig. 3 — makemigrations only reads your models and writes a migration file; migrate is the step that actually touches the database. Always run them in this order.

Core commands

terminal 
# Generate migration files from model changes
python manage.py makemigrations
python manage.py makemigrations blog        # scope to one app

# Apply pending migrations to the database
python manage.py migrate

# Preview the raw SQL a migration will run (without applying it)
python manage.py sqlmigrate blog 0001

# List all migrations and which are applied ([X]) vs pending ([ ])
python manage.py showmigrations

# Roll back to an earlier migration
python manage.py migrate blog 0001

# Combine many small migrations into one (housekeeping)
python manage.py squashmigrations blog 0001 0004

Anatomy of a migration file

blog/migrations/0001_initial.py 
from django.db import migrations, models

class Migration(migrations.Migration):

    initial = True
    dependencies = []

    operations = [
        migrations.CreateModel(
            name='Author',
            fields=[
                ('id', models.AutoField(auto_created=True, primary_key=True)),
                ('name', models.CharField(max_length=100)),
                ('bio', models.TextField(blank=True)),
            ],
        ),
    ]

Data migrations (advanced)

Besides schema changes, migrations can also transform existing data using RunPython:

from django.db import migrations

def set_default_author(apps, schema_editor):
    Post = apps.get_model('blog', 'Post')
    Author = apps.get_model('blog', 'Author')
    default_author, _ = Author.objects.get_or_create(name='Unknown')
    Post.objects.filter(author__isnull=True).update(author=default_author)

class Migration(migrations.Migration):
    dependencies = [('blog', '0003_add_comment')]
    operations = [migrations.RunPython(set_default_author)]
Common pitfall: editing a migration file that has already been applied on a shared/production database causes Django's migration history to go out of sync. Once a migration is applied elsewhere, create a new migration to make further changes instead of editing the old one.

Why migrations exist

Before Django's migration framework (pre‑1.7), schema changes had to be applied by hand-writing ALTER TABLE statements against every database instance — error‑prone and impossible to keep in sync across a team. Migrations solve this by treating the schema as code that lives in version control: every model change is captured as a small, ordered, replayable Python file. Anyone (or any deployment pipeline) can reconstruct the exact same schema by running migrate from a clean database.

Migration state vs. database state

A subtle but important theoretical point: makemigrations does not compare your models to the actual database. It compares them to the migration state — the schema that Django computes by replaying every existing migration's operations in order, purely in memory. This is why deleting or hand‑editing a migration file can silently desynchronise what Django "believes" the schema is from what's really in the database, and why showmigrations and sqlmigrate are the safe way to inspect that computed state before trusting it.

Atomicity and the dependency graph

On databases that support transactional DDL (PostgreSQL, SQLite), Django wraps each migration in a single database transaction by default — if any operation inside it fails, the whole migration rolls back rather than leaving the schema half‑changed. Each migration file also declares a dependencies list naming other migrations (potentially from other apps) that must be applied first. Django resolves all migrations across all apps into a single directed graph and applies them in an order that satisfies every dependency — which is how, for example, a migration in blog that adds a ForeignKey to Django's built‑in auth.User correctly waits for auth's own migrations to run first.

Advantages of Django's migration system (frequent exam question)

  1. Version-controlled schema: migration files are checked into Git alongside the code, so schema history is tracked and reviewable like any other change.
  2. Reproducibility: any developer, CI server, or production deployment can rebuild the exact same schema by running migrate from empty.
  3. Team safety: multiple developers changing models independently each get their own migration file, which Django's dependency graph then merges/orders correctly instead of causing silent schema drift.
  4. Reversibility: most operations can be unapplied by migrating to an earlier target, useful for rolling back a bad deployment.
  5. Data + schema together: RunPython operations let data transformations travel through the same versioned, ordered pipeline as schema changes.
  6. No manual SQL required: developers describe changes at the Python/model level; Django generates the correct dialect-specific DDL for the configured database engine.
